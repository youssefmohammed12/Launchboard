# Launchboard v1.2.0 — Action Center Design

**Status:** Stages 0–6 implemented and verified locally; migration 004 and production release remain approval-gated
**Date:** 2026-11-07
**Branch:** `feature/action-center-v1.2`
**Baseline:** `ui-v1.1.0` / `38cadda`
**Related plan:** `docs/v1.2-action-center-plan.md`

## 1. Design goal

Make Launchboard a more action-oriented personal opportunity workspace. A user should be able to record concrete next actions, see what is overdue or due next, complete work, and keep that work connected to the opportunity it belongs to.

Keep the product focused. Launchboard is not a marketplace, a general-purpose project manager, or an automatic application service. Users continue discovering opportunities on external platforms.

## 2. Findings from the current implementation

### Opportunity domain

- The shared `Opportunity` contract lives in `packages/domain/src/opportunity.ts`.
- Each opportunity currently owns root-level `deadline` and `followUpDate` date-only fields.
- Nested collections are `activities`, `interviews`, `contacts` and `materials`. Their IDs are stable within the parent opportunity.
- Activities are dated history entries, not pending work. Interview entries have their own date, optional time and Scheduled/Completed/Cancelled state.
- Shared controlled values, field limits, date rules and backup contracts live in `@launchboard/domain`; frontend wrappers re-export those contracts.

### Calendar and Dashboard

- `src/utils/calendar.ts` derives Calendar and Dashboard events from active opportunities.
- Existing event types are Deadline, Follow-up and Interview. Archived opportunities are excluded.
- Deadlines are suppressed for Offer and Rejected opportunities. Follow-up dates remain eligible regardless of status.
- Scheduled interviews appear in upcoming/overdue ranges; Completed and Cancelled interviews remain in the month calendar as history.
- Calendar and Dashboard use validated local `YYYY-MM-DD` dates. The Dashboard currently has a Next 7 Days event summary, not a task-focused Today list.
- The separate Deadlines view and follow-up utilities also read the existing opportunity date fields.

### Local persistence and recovery

- Local mode stores the complete opportunity collection under `launchboard.opportunities.v1`.
- `normalizeOpportunityRecord` rebuilds records and supplies safe defaults for missing optional fields and child collections.
- The raw recovery key is `launchboard.recovery.raw.v1`. Unreadable or duplicate data is preserved before repair; writes are blocked when preservation cannot be verified.
- Local edits persist a complete candidate collection before publishing the new React state. There is no separate local CRUD database for child records.

### Authenticated API and database

- API mode loads an account-scoped `OpportunityCollection`; each resource includes an opportunity version, and the collection includes a user-level revision.
- Nested mutations use `mutateAggregate`: fetch the latest opportunity, apply the change, then send a version-checked `PUT /opportunities/:id`. The server validates ownership and writes the aggregate transactionally.
- The server currently replaces nested child collections within the same transaction and returns the refreshed aggregate.
- SQL migrations 001–003 define opportunities and their child tables. Child records reference the parent opportunity; user ownership is enforced through the owning opportunity and user-scoped queries.
- The API has strict Zod request schemas, optimistic concurrency, and a shared backup import/export service. Those are the correct extension points for tasks.

### Backups and CSV

- JSON backup schema v1 is the full-fidelity format. The frontend and server both normalize opportunity records through the shared domain backup normalizer.
- Both JSON import paths currently accept only the current backup schema version.
- CSV is intentionally a tabular/summary format, not a full-fidelity backup. JSON remains the canonical way to preserve the complete opportunity aggregate.

## 3. Recommended task domain

Tasks should be a new child collection on an opportunity, not a standalone top-level collection.

### Proposed task shape

```ts
interface TaskEntry {
  id: string;
  title: string;
  notes: string;
  priority: Priority;
  dueDate: string;      // local YYYY-MM-DD, or '' when unscheduled
  completed: boolean;
  completedOn: string;  // local YYYY-MM-DD, or '' when not completed
}
```

Recommended rules:

- Every task belongs to exactly one opportunity. The parent relationship supplies its opportunity identity; do not duplicate `opportunityId` inside the nested record.
- Reuse the existing `Priority` values: Low, Medium and High. Default new tasks to Medium.
- Require a non-empty title. Keep notes optional.
- Proposed initial limits: 100 tasks per opportunity, 160 characters for the title and 1,000 characters for notes. Keep limits centralized in `@launchboard/domain`.
- Due dates and completion dates are local date-only values. Do not add a time-of-day field in v1.2.
- Completing a task sets `completed = true` and records `completedOn` as the current local date. Reopening clears `completedOn`. Validate the date and the relationship between these fields.
- IDs must be unique within the opportunity. Tasks preserve their array order; the server can persist that order with a position column.
- Do not add recurring tasks, subtasks, task dependencies, tags or task-specific notification channels in this release.

The completion date is included because the later Weekly Goals and Review feature needs to know which week a task was completed. It is a user-data date, not a server audit timestamp.

## 4. Keep existing opportunity dates distinct

The three existing date concepts retain their current meanings and behavior:

| Existing record | Meaning after v1.2 |
|---|---|
| Opportunity deadline | Application/eligibility deadline; remains an opportunity date and Calendar event |
| Opportunity follow-up date | One general follow-up reminder date; remains an opportunity date and Calendar event |
| Interview date/time | An appointment with its own status and optional time; remains an interview and Calendar event |
| New task due date | A concrete, named action the user intends to complete; appears in Action Center and Calendar |

No migration should automatically create tasks from deadlines, follow-up dates, interview appointments or activity history. No existing field should be replaced by a task field.

A user may intentionally create a task on the same date as an existing opportunity event. Those are separate records with different meanings; show clear type labels rather than silently merging or deleting either one.

## 5. Persistence and API design

### Local mode

- Add `tasks: TaskEntry[]` to the shared Opportunity contract.
- Keep the existing `launchboard.opportunities.v1` key; this is an additive, backward-compatible field inside the existing collection.
- Update local normalization so older records with no `tasks` field become `tasks: []`. Repair malformed task children without discarding an otherwise valid opportunity.
- Preserve the existing recovery-first write policy. Do not add a second task localStorage key.
- Extend JSON backup normalization and round-trip tests so tasks are retained.

### Authenticated API mode

- Add `tasks` to the writable opportunity aggregate and returned `OpportunityResource`.
- Extend strict Zod validation with title/notes/date/priority/completion checks, task-count limits and duplicate task-ID checks.
- Add an additive migration **004** for a `tasks` child table. Recommended columns: internal ID, `opportunity_id`, public task ID, position, title, notes, priority, nullable due date, completion flag and nullable completion date.
- Add a foreign key to `opportunities` with cascade on permanent parent deletion; add uniqueness for public task ID and position within the parent, plus an index supporting parent/due-date reads.
- Extend aggregate mapping, child selection, child replacement and backup import insertion to include tasks. All task writes must occur in the existing parent aggregate transaction.
- Keep user ownership enforced through the user-scoped parent opportunity lookup. Do not accept a free-standing client-supplied owner ID.
- Reuse the current `GET` + version-checked `PUT` flow. A task mutation increments that opportunity's version and the existing user collection revision. Do not introduce an independent task revision system or unversioned task endpoints in v1.2.
- Archived opportunities retain their tasks. Those tasks are hidden from the active Action Center and Calendar while the parent is archived; they reappear if the opportunity is restored. Existing deletion/Undo behavior must keep task data with its parent.

### Backup compatibility

- Make JSON backup schema **v2** the export format once tasks are added.
- Continue accepting schema v1 backups. Normalize v1 opportunities to `tasks: []`; accept v2 task data through the shared normalizer.
- New v2 exports must include all tasks, including completed and unscheduled tasks.
- Extend API backup import/export and local restore/migration paths together. Do not declare the release complete until local and API JSON round-trips pass.
- Keep CSV as the existing tabular summary format; do not describe it as a full backup. JSON is the full-fidelity format for tasks and the whole aggregate.

## 6. Action Center behavior

### Classification

The Action Center is derived from the loaded opportunity collection; it is not a second persisted task list.

For active opportunities only, classify incomplete tasks as follows:

- **Overdue:** valid due date earlier than today's local date.
- **Today:** valid due date equal to today's local date.
- **Upcoming:** valid due date later than today's local date.
- **Unscheduled:** no due date (`''`).
- **Completed:** completed tasks, shown separately or through a Completed filter; never counted in the four open-task groups.

Invalid dates must not be assigned a fallback date. Use the same shared date helpers as Calendar. The default Action Center should show open work first and provide an accessible way to inspect completed tasks.

Within dated groups, sort by due date and then priority (High, Medium, Low), with stable opportunity/task title tie-breakers. Keep the ordering deterministic so local and API modes agree.

### Task interactions

- A user can create a task from the Action Center by selecting an active opportunity.
- A user can also add/manage tasks from that opportunity's details context, with the parent preselected.
- The task row/card shows the task title, priority, due date, opportunity and completion control.
- Editing, completion/reopening and deletion use the same persistence boundary as the other nested records.
- Completing a task updates the Action Center immediately after a successful save. A failed local write or API request must leave the visible task unchanged and show a recoverable error.
- Opening the opportunity context must remain possible from each task row.

### Dashboard

Add a compact **Today** / **Today's Focus** section showing overdue and due-today open tasks, with a clear link to the full Action Center. Keep the current Next 7 Days section for existing deadline, follow-up and interview events; do not turn the Dashboard into a second full task manager.

### Calendar

- Add a distinct Task event type and a Tasks filter.
- Show incomplete tasks that have valid due dates. Unscheduled tasks do not create Calendar events; completed tasks remain in the Action Center's Completed view rather than cluttering the active calendar.
- Preserve the existing deadline/follow-up/interview filters, eligibility rules and event history behavior.
- Task events must be visibly distinguishable from legacy date events. Selecting one should take the user to the task's edit/completion context, not merely open an unrelated opportunity form.

## 7. Navigation and scope

- Add an Action Center item to the main navigation and a matching view in the shared frontend view type.
- Render the same Action Center behavior in local and API mode.
- Keep one shared task classification utility used by the Action Center and Dashboard, with Calendar event derivation consuming the same task contract.
- Do not include tasks in Global Search in v1.2 unless it becomes a small, clearly testable extension after the core release is stable.
- Browser/email push notifications, automatic scheduling and mandatory external services remain out of scope. In v1.2, reminders mean clear in-app visibility through Action Center, Dashboard and Calendar.

## 10. Stage 0 decision record

| Question | Recommended decision |
|---|---|
| Task relationship | Required child of one opportunity |
| Task storage | Nested in the Opportunity aggregate; relational child table in API mode |
| Priority | Reuse Low / Medium / High |
| Due date | Optional local date-only string |
| Completion | Boolean plus local completion date for later weekly review |
| Action Center data | Derived by flattening tasks from active opportunities |
| Existing deadline/follow-up/interview dates | Remain distinct; no automatic task conversion |
| API writes | Existing version-checked opportunity aggregate transaction |
| Local compatibility | Existing localStorage key; missing tasks normalize to [] |
| Backup format | Export v2; continue importing v1 as tasks=[] |
| Notifications | In-app only in v1.2 |
| CSV | Remains a tabular summary; JSON remains full-fidelity |

These decisions are the Stage 0 implementation recommendation. Revisit a decision only if implementation evidence reveals a concrete conflict with the current repository contract.

## 14. Stage 3 task-operation implementation — 2026-11-07

**Status: Complete and locally verified.**

### Domain lifecycle

- `TaskDraft` contains only editable content fields: title, notes, priority and due date. The task ID and lifecycle fields are managed by operations.
- `addOpportunityTask` creates a new open task, trims editable text, validates the full result, rejects duplicate IDs and enforces the per-opportunity cap.
- `updateOpportunityTask` edits content without changing ID or completion state. An unchanged edit is a no-op.
- `completeOpportunityTask` requires a real local YYYY-MM-DD completion date. Repeating completion is a no-op.
- `reopenOpportunityTask` clears the completion date. Repeating reopen is a no-op.
- `deleteOpportunityTask` removes only the matching task and keeps remaining task order.
- The functions return immutable results and explicit failure reasons; they do not perform I/O or depend on browser/server runtime.

### Persistence adapters

- `commitLocalTaskMutation` requires one unambiguous parent, runs the operation against its task list and persists a complete candidate through the caller-provided recovery-aware commit. A failed local write reports `save-failed` and leaves the previous state untouched.
- `commitApiTaskMutation` loads the latest opportunity resource before invoking the operation. Changed tasks are persisted by `HttpOpportunityRepository.updateTasks`, which delegates to the existing version-checked aggregate PUT. No separate task route or revision is added.
- API conflict handling is deliberately conservative: a 409 is surfaced to the UI and not automatically replayed against a newer task list, avoiding lost updates.

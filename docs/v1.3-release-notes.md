## What changed

Quick Capture gives you a review-first way to start an opportunity from a public job-posting URL. Where a supported employer or applicant-tracking-system (ATS) page exposes usable details, Launchboard can suggest them. You can correct every value, continue manually, and save only after explicit confirmation.

- **Supported public job pages:** provider-aware adapters and carefully bounded metadata fallbacks cover a range of employer career sites and ATS platforms, including Greenhouse, Ashby, Workable, Lever, SmartRecruiters, Workday, BambooHR, Breezy, Teamtailor, Personio and Rippling where the relevant public posting/feed is available.
- **Review before save:** extracted values are editable; partial, unsupported, blocked or ambiguous pages can continue through manual entry. Preview is read-only and does not create an opportunity.
- **Field-level evidence:** the review form identifies the source and confidence for extracted fields. Missing or ambiguous details remain blank rather than being guessed.
- **Structured job details:** opportunities can hold multiple locations, department, team, workplace type, employer employment type, posted date and structured compensation while preserving the original free-text compensation field.
- **Duplicate warnings:** URL and title/company matching help identify existing active or archived opportunities without silently merging records.
- **Backup and compatibility:** the release adds optional structured fields while preserving older opportunities and backup imports. JSON backup schema v3 carries the structured details; CSV remains a tabular summary.
- **What's New:** the release appears in the in-app version history, with a first-use Quick Capture spotlight for signed-in users.

## LinkedIn support and future work

LinkedIn URLs remain valid opportunity links, but **automatic LinkedIn lookup is disabled**. Launchboard does not send LinkedIn URLs to its capture server or attempt to scrape/copy LinkedIn pages. Users can continue manually and retain the original URL.

The broader LinkedIn improvement is deliberately deferred. Future research/implementation may explore a deterministic parser for job details that the user manually pastes, plus an optional separate employer/ATS URL that the user supplies. The original LinkedIn URL must remain the saved opportunity link; any metadata must be sourced from user-pasted text or the supported external ATS page. This is not part of v1.3.0.

## Data and deployment notes

- Additive database migration 005_opportunity_job_details.sql adds the structured job-detail storage. It was already recorded as applied to the Launchboard TiDB database before this production release; no migration was re-run as part of deployment.
- The Quick Capture preview endpoint is read-only with respect to opportunity records. It requires an active authenticated session, CSRF/origin checks and is protected by the Vercel edge rate limit (five preview requests per minute per IP).
- LocalStorage-only mode remains manual-entry-only. Authenticated API mode is required for public page lookup.
- The persistent QA Preview shares the production database. Its manual QA must not be treated as a sandbox or used for destructive CRUD testing.

## Post-release routing correction — 8 November 2026

The initial v1.3.0 Production deployment served the homepage, but nested authentication routes returned 404. The source-based Production deployment used the repository-root `vercel.json`, which was missing the `/api/:path*` rewrite to the catch-all function. The separate `deployment/vercel.json` already contained that rewrite, so the routing configurations had diverged. The Preview used in the earlier QA pass was also built from commit `db155ff`, not the original Production candidate commit `898a743d18af128f6dea1d21013623ba74744201`; it was therefore not a valid same-candidate release check.

The correction restored the nested API rewrite before the SPA fallback in root `vercel.json` and aligned the catch-all function filename to `api/[...].ts`. A candidate-specific Preview and the final Production deployment were both built from exact commit `4c1b3a035cb6a7c2507b546456d3edd39a0710e3`. The Preview passed explicit auth/API route probes before deployment, and the canonical Production domain passed the same probes afterwards.

This changes the release acceptance standard going forward: every release must verify Preview source SHA equality, SPA routes, health/readiness, critical nested authentication/API routes, the actual Vercel routing configuration used, and the canonical Production domain after deployment. See `docs/deployment-readiness.md` for the mandatory checklist. An expected unauthenticated 401/403 verifies route reachability only; it is not proof of successful real-user authentication.
